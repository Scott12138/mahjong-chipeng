### ★★★ 引擎级认知修正：`UIOpacity` 对 Graphics 是「一次性覆写」

> **它推翻了本工程流传两轮的错误结论**「`UIOpacity` 对 `Graphics` 不生效」，
> 而那条错结论刚刚炸出一次全屏黑屏。

- **机制**：引擎在 `opacity` **变脏的那几帧**，把子树每个顶点的 alpha **整个替换**成级联值
  （`cocos/2d/assembler/utils.ts: updateOpacity` → `vb[i] = (vb[i] & 0x00ffffff) | (alpha << 24)`，
  **是替换，不是乘系数**；触发点 `batcher-2d.ts: _handleUIRenderer`，Graphics 走 COLOR 分支）。
  **tween 一停就不再置脏**；此后顶点数据一旦被重建（`render-data` 的 chunk recycle / allocate），
  alpha 就**回落成 Graphics 自己烘焙的 `fillColor` 值**。
- **后果分两种**：
  · **多档**图形（四层墨晕）→ 回落成各层各自的 alpha → 分层**会回来**；
  · **目标非 255 的单档**图形 → 回落成 255 → 更不透明，且**永不恢复**。
- **新判据**（已写进 `UIFactory.ts` 铁律段，取代旧的"看内部有没有多档 alpha"）：
  只有两种情况可以用 `UIOpacity` —— ① 目标值 **0**（引擎里是硬开关，整棵子树跳过渲染）；
  ② 目标值 **255** 且内部单档（回落值恰好等于目标值）。
  **凡目标值是中间值 → 一律 `alphaPainter` 烘焙。**
- 全工程 **16 处** `UIOpacity` 按新判据复查：只有失败动效的压暗层 **1 处**违规，已修。
- ⚠️ 更隐蔽的一条：**祖先的 `UIOpacity` 一样会抹平后代** ——
  `PageManager.open()` 给每个页面节点挂了 UIOpacity 做 0.22s 转场淡入，
  在它脏着的那 220ms 里，**整页所有 Graphics 的分层都是被抹平的**。

### 它炸出的 bug：失败动效全屏黑屏（已修）

- **现象**：判负后 520ms 起**整屏 `#22201C`**（正好 = `CFG.COLOR.INK`），
  四角与中心完全同值、**纯黑像素占比 0%**（→ 排除"Canvas 清屏黑"，锁定为压暗层不透明），
  +3.7s 仍全黑，失败面板"已开"却被整个盖住。
- **根因**：压暗层（全屏 INK 矩形，`fillColor` alpha=255）用 UIOpacity 淡到 `DIM_ALPHA=0.10`；
  tween 期间每帧被覆写成 25（**看着完全正常 —— 所以上一轮"通过"了肉眼检查**），
  tween 一停（0.27+0.18=0.45s）→ 顶点重建 → 回落 255 → **永久全黑**。
- **修复**：改回 `alphaPainter` 烘焙。复验 520ms 采样 `216,210,193`（比 300ms 暗一档 = 正好 10% 墨）。
- **教训（可复用）**：`UIOpacity` 的 tween **终点值必须复验**，不能只看 tween 期间"像不像"。
  判据：采样像素，看它是否等于**预期值**，而不只是"看起来对"。

### 1. 「?」→「规则」—— 结论：**必须放弃「绝对居中」**

## 【S22 交付：胶囊被画成椭圆 —— "边缘突出"的真凶】（2026-10-02 13:10）

用户反馈"这几个按钮边缘突出的地方还是没修好"，三张图仍是首页主按钮 / 局内返回 / 广告弹窗。
S21 修的是柔影（"漂"），**这次是另一回事**。

### 真因（一句话）
**Cocos `Graphics.roundRect(x,y,w,h,r)` 把两个方向的半径分别夹取**：

```js
var rx = min(r, abs(w) * 0.5) * sign(w);   // 999 → w/2
var ry = min(r, abs(h) * 0.5) * sign(h);   // 999 → h/2
```

传 `RADIUS_PILL = 999` 时 `rx ≠ ry` → 四个角是**椭圆弧** → 整块读成**椭圆**，
不是 CSS `border-radius:999px` 的**胶囊（stadium）**。
外圈（`w+8 × h+8`，r=1003）更夸张：rx=94 / ry=32 → 鼓成**杏仁形**，在两端"突出"。

### 为什么以前没发现
同一个 `draw3dFace` 里，**渐变面层走 `halfWidthAt()`，那个函数本来就正确地夹了**
（`R = min(r, min(w,h)/2)`）→ 面层是**真胶囊**；描边/外圈走 `fillBox` → **椭圆**。
"椭圆描边 + 胶囊内胆"叠在一起，在 720×1280 的整屏缩略图里看不出来，
一到真机（1264 宽、逐像素放大）就非常刺眼。

### 修法（单点）
`UIFactory.ts` 新增 `clampRadius(w,h,r) = max(0, min(r, min(|w|,|h|)/2))`，
`fillBox` / `strokeBox` 统一走它。对本来就小的圆角（面板 26、槽位条 14、道具 16、
规则 15、重玩 22、槽格 8…）**不生效 → 零回归**；只改到"半径 ≥ 半高"的那几个。

### 顺带修好的
- **进度条轨道**：`drawProgressBar` 里写的是 `const r = w / 2  // 胶囊` ——
  同样中招（544×14 传 272 → rx=272 / ry=7 → 椭圆）。现在自动变回胶囊。
- 所有 `createButton` 默认 `RADIUS_PILL` 的按钮：首页主按钮、结算页按钮、
  RewardGate 的「看广告 获得」/「分享给朋友」、胜利/失败页按钮。

### 验收（ASCII 轮廓图逐格比，比截图对照靠谱）
`fillBox` 修完后把 720×1280 的二值轮廓打成字符画，与设计稿逐行对齐：
- **返回键**：修前 y1094~1108 整段**没有暗像素**（椭圆的左上收进去了），
  修后 `y1089/1091/1093` 的顶带跨度、`y1129~1139` 的双线、`y1141~1153` 的底带
  **全部与设计稿同格**。
- **首页主按钮**：修前顶带只跨 x257~343（椭圆），修后跨 x233~365 = 设计稿。
- **弹窗红钮**：修前上下都收成尖（杏仁），修后 `y482~485` 平顶 + `y570~584` 平底。
- 回归抽查（设计稿 vs 游戏实拍，HUD 五个区域）：顶部条/进度条/槽位条/道具栏/返回重玩
  平均差 8~12 级、>30 的像素 6~10%，全部来自**文字字形的抗锯齿**（字体不同），
  结构无回归。

### 交付物
`docs/verify/S22/`：`01-首页主按钮.png`、`02-局内返回键.png`、`03-弹窗按钮.png`
（设计稿 / 真机修前 / 修后 三栏对照）+ 三张修后整页 + `device/真机预览二维码.png`。
真机码：**包体 2 553 665 字节 = 2.44MB**，解码 OK。

### 经验（已同步进技能）
> 在 Cocos 里画"胶囊"**永远不要直接把 `RADIUS_PILL` 之类的超大 radius 丢给
> `Graphics.roundRect`** —— 它按 `rx = min(r, w/2)` / `ry = min(r, h/2)` 分别夹，
> 得到的是**椭圆**。要么自己先 `min(r, min(w,h)/2)`，要么像 `halfWidthAt` 那样手算轮廓。
