### 二、关键实测（归档 `docs/verify/S7.9/开局可点分布/`）

每关 400 次**确定性**种子（`seed=(i+1)*2654435761`，任何人跑结果逐位一致）：

| 关卡 | 平均可点 | ≥6 达标率 | ≥5 达标率 | 门槛 6 兜底率 | 门槛 5 兜底率 |
|---|---|---|---|---|---|
| L2 | 4.02 | 8.5% | 33.0% | 2.9% | ≈0 |
| L3 | 3.83 | 5.3% | 24.5% | 11.3% | ≈0 |
| L4 | 3.75 | **0.8%** | 16.8% | **72.5%** | **0.06%** |

**核心结论：门槛 6 是失效的** —— 多层堆叠的顶层天生窄，「≥6」是罕见事件，
40 次采样**整体作废**，最终仍用「2~5 张可点、且**从未跑过可解性校验**」的兜底局。
（早前 150 次随机种子测得 L4 = 42.7%，与 72.5% 同属「单次 ≥6 率约 1%」下的样本波动，**以 400 样本为准**。）

⚠️ 复现要点（踩过的三个坑）：副本目录 + 相对 import 改 `./X.ts` + **类型名必须走 `import type`** +
副本 `Generator.ts` 末尾补 `export { buildGrid, sampleCells, buildBag, placeTiles }`；
Node 用 `--experimental-transform-types`（内置，不需要 tsc）。

- 遗留：`AudioService.setMuted / toggleMuted` 有实现但**全工程无人调用**（界面没有静音开关）。

## 2. ★ 本轮最重要的架构认识

### 2.1 旧堆叠模型的病根（三条叠在一起，必然贴下缘）
1. 层是**副产品**：先铺满格点，装不下才在**同一批格点**上再摞一层 → 层与层**位置完全重合**；
2. 纵向"谁压谁"由**行号**决定（`depth = 行号反序 × 1000`）；
3. 行的分布是**下密上疏**（`WEIGHT_Y = 0.7`）。
→ 三者合起来 = 牌堆必然是一坨**贴着下边缘的小土丘**、上方一大片空白（用户截图精确命中）。

### 2.2 新模型：floor 升为一等公民
`先定层数 F = clamp(ceil(count/PER), 1, MAX)` → 按 `DECAY^k` 由下往上递减分配张数（最大余数法）
→ 每层是一个**中心独立随机**的"片"（整堆落点 `DRIFT` + 层间错开 `LAYER_DRIFT`）
→ 片内按**切比雪夫距离**加权聚集（`TIGHT`）→ 层间纵向错开 `GAP`，**位移以中间层为基准上下对称**。

**★ 开局可点是物理结果，不是运气**：顶层张数最少 → 顶层的片最小 → **盖不住下一层**
→ 下层的牌从缝里露出来。

**★ 深度公式唯一口径**（首次铺牌与洗牌重排共用，历史上两处各写一遍写错过一次）：
`depthOfCell(grid, cell) = cell.floor * 100000 + cell.layer * 1000 + (grid.rows - 1 - cell.r)`

### 2.3 ★★ ③ 与 ④ 为什么必须一起做
牌放大 1/4 → 格点从 **6×11=66 掉到 5×8=40**，而 L4 有 96 张：
**"同格叠放"再也补不上缺口**（40 格摞到 96 张会变成均匀方块）。只能靠**分层**消化。
单独放大不改堆叠模型 → 96 张直接溢出牌堆区。

### 2.4 量化验收（全部通过）
| 项 | 结果 |
|---|---|
| 分词（由下往上） | L2 16/11/9（3层）· L3 21/16/11/9/6（5层）· L4 30/22/16/12/9/7（6层） |
| 开局可点 | L2 5–9 · L3 5–9 · L4 5–8（`MIN_PICKABLE=5` 成立） |
| 越界 | 四关各 20 局，**出区牌 0 张** |
| 认证（40 局） | `DRIFT 0.10` → L4 30/40；**`DRIFT 0.30`（采用）→ 26/40**；两档开局可点中位数都是 7 |
| 生成耗时 | L4 约 88–139ms |

### 2.5 复活新规则的两个要点
- `clearN = ceil(槽容量 × 0.5) = 4`，消**槽内最后 4 张**（数组尾部），保留前 4 张；暂存架不动。
- ★ **重排的可解性校验必须把"槽里保留的那几张"算进去**
  （`planReshuffle(..., this._slots.map(e => e.key), ...)`），

  终局会剩 1~2 张消不掉的牌。**收口只需把比例改成 `1/4`(2张) 或 `3/4`(6张)**。
- 按钮文案改成**从参数算**：`` `看广告复活（消 ${reviveClear} 张 + 重排）` ``。

## 3. ★★ 本轮最有价值的方法论（已写进 skill）

### 3.1 `fill:<n>` —— 用"预判"代替"撞运气"的冒烟动作
旧的 `dirty` **允许撞上「吃」**（这正是它能抓「吃」动效的原因）→ 槽内凑出连号就消 →
**槽永远到不了 8 张** → 永远逼不出「槽满判负」。
新增 `fill:<n>`：把"这一步会不会消"**完整预判**一遍（碰/杠/吃都算，规则必须与 `MatchRule.findMatch` 一致），
只点不会引发消除的牌 → **必定**填满槽。
> **推广**：任何"要走到某个极端状态才能触发"的功能，都需要一个**专门构造该状态**的动作，
> 而不是指望随机操作撞上去。

### 3.2 无头探针的 `sync.sh`（别再手工改 import）
手工字符串替换 import 的翻车方式：源码里**多 import 一个符号** → 替换静默失配 →
报 `does not provide an export named 'X'`，**报错指向被 import 的文件**（让人以为数据文件坏了）。
`sync.sh` 的做法：① 扫 `export interface/type` 自动拿类型名单拆 `import type`；
② **路径压平成 `./X.ts`**（探针目录是平铺的，源码里的 `../CFG` 只补后缀会被解析到 /tmp/CFG.ts）；
③ 追加 `export { 内部函数 }`（先扫已有导出，否则 `Duplicate export`）。

### 3.3 ★★ 纯数据怎么"看图"：数据 → SVG → 无头 Chrome 截图
分层几何这种问题读数字太慢。折中：探针直接输出 SVG（每张牌一个 `<rect>`、
**按层上色**、开局可点描橙框、画出牌堆区/槽位条边界），再用已有的无头 Chrome 截 PNG。
- **不需要起游戏**，几何对错一眼看出；
- 支持 **CLI 覆盖参数做 A/B**（`DRIFT=0` vs `0.30` 各一张并排）→
  "为什么选这个值"有了**可复看的证据**（本轮就是靠这两张图定的参数）；
- 机器判（程序算 rect 是否出区）+ 肉眼判（图上看有没有出框）**互为交叉验证**。

### 11.3 ★ 音效候选的技术路线（"借真人干声 + 重写声调"）

### 12.1 音效「加长 + 尾音」：三层，全时域，不碰谐波
新增在 `tools/make-voice.py` §四：
`trim2()` / `_acf_at()` / `steady_tail()` / `sustain()` / `vibrato()` / `room_tail()` / `lengthen()`
/ `period_corr()`；§五 `build_v2()` + `plot_compare()`（产出 `03-音效加长前后波形对照.png`）。

| 层 | 函数 | 做什么 |
|---|---|---|
| ① 非对称裁剪 | `trim2(head_th=0.06, tail_th=0.012)` | 头照旧清静音，**尾只砍 1.2%** 保住真人渐弱 |
| ② 周期对齐拖长 | `steady_tail()` + `sustain()` | 从"最后一个**还有能量且仍是稳态元音**"的位置取一个基音周期重复 |
| ③ 房间尾音 | `room_tail()` | 指数衰减噪声 IR → FFT 卷积 → 1.6ms 低通（高频先衰） |

**★ 本轮最贵的教训（三条，全都"报错指向错误方向"）**
1. 🔴 **在已被裁剪的成品上加长 = 硬接一截**（自然衰减早没了）→ 必须**从 raw 原料重建**：
   `raw_wav()` → resample → `trim2` → 加长。
2. 🔴 **`trim()` 的 6% 阈值把真人尾音切掉了**：「吃」6% 下 0.287s、1.2% 下 0.337s，**白丢 50ms**。
3. ★★ **周期对齐"从哪取周期"决定成败**：必须同时满足**能量 + 周期性**并**吸附到声门脉冲峰值**。
   只看能量 → 滑进衰减区 → 复读出来是**机器嗡声**（时长数字变长了，实际只有 −62~−68dBFS，
   等于没声音）。**判据是逐 50ms 打 dBFS，不是看时长**。
4. **自相关窗长必须随音高自适应**（≥4.5 个周期）：固定 30ms 对 74Hz 男声装不下 3 个周期
   → r 假性偏低 → 云希两个候选都"找不到稳态段"。`_acf_at` 按粗估周期 ×4.5。
5. **`contour_of` 必须加能量门 `rms_th=0.18`**：尾部阈值放宽后轻声段 F0 跟踪不可靠，
   调值 RMSE **从 1.38 假涨到 22**；加门后回到 2.1~2.6。
6. **`seam_check` 是伪值**（同一份代码在 101Hz / 280Hz 上差 10 倍）→ 废弃，改 `period_corr`。
   死代码 `tail_f0` / `loud_anchor` 一并删除。

### 13.3 「一个嘴咬 N 次」：三口重叠的几何问题（`bites`）
三口在时间上**重叠**（`EAT_SUCK` 0.20s > `EAT_STAGGER` 0.13s）。
每口各起一个嘴 → 两个**同位置、同线宽、只有高度不同**的弧叠在一起 → 读成"上下颚各长出两条"的重影。
demo 的 canvas 版用 `max()` 合并成一条曲线绕开（逐帧重绘才做得到），**tween 驱动做不到**。

→ `spawnJaw` 加 `bites` / `reopenDur`：
`张开(openDur) → [咬合(biteDur) → 再张开(reopenDur)]×(bites-1) → 咬合 → 停留`
**只要 `reopenDur = EAT_STAGGER − EAT_MOUTH_BITE`，每次"合拢的开始"就精确落在该口"牌到位"的时刻。**

| 编号 | 名称 | BPM | 调式 | 定位 |
|---|---|---|---|---|

### 16.4 ★ 四个"听不到声音时怎么验收"的手段（本轮最大的方法论收获）
1. **声部活跃段 RMS + 目标配平表**。音色经滤波后电平天然差很远（`i_bass` 单音峰 0.50、
   `i_clap` 整轨 −35dB），手调增益是猜 → 给每个声部定目标（lead −13 / bass −14 / kick −13.5 /
   pad −20 / hat −24 …dB），量出来补回去，上限 ±12dB。
   **关键：必须用"活跃段 RMS"**（只在真的在响的帧上求），用整轨 RMS 会把吊镲判成 −35dB
   然后狂补 +20dB，一响就炸。
2. **统一 10ms 收尾淡出**。所有合成音色都是"指数衰减 + 到点截断"，而**截断那刻幅度不为零**：
   实测 `i_bass` 到 dur 还剩 **21%**、开镲（tau 0.15 但 dur 0.07）剩 **63%** → 每小节八次爆音。
   放进 `@memoized` 包装器里统一做，**保证不漏任何一个音色**（漏一个就是一处随机爆音）。
3. **循环接缝的正确口径**。❌「循环点跳变 ÷ 峰值」在 A/E 上高达 0.32/0.27，看着像爆音，
   实际测的是**"循环点正好落在强拍上、底鼓+吊镲攻击"**那一下 —— 强拍本来就该跳，会被带沟里。
   ✅ 改成「循环点跳变 ÷ 曲内强拍跳变中位数」：A 1.41 / B 0.87 / C 2.71 / D 0.56 / E 0.83，
   全部 **≤ 曲内最强强拍** ⇒ 合格。
4. **可复现实测**：连续两次 `--page`，五段 m4a 的 md5 逐字节一致。
   ⚠️ 过程中两次得到**假通过**：一次是 `cd` 相对路径算错（重跑压根没发生），
   一次是脚本在 `analyze()` 崩了而 **m4a 是在 analyze 之后才写** → 旧文件原样保留。

### 16.5 揪出的两个"编译运行都不报错"的 bug
- **主奏被叠了 4 层**：`s.melody('lead', lead, b - bar, ...)` 里 `bar = b % 4`，
  于是 b=0..3 时 `b - bar` **全等于 0** —— 同一句 4 小节旋律在相邻 4 小节各铺一遍，
  主奏声部 max 冲到 **1.36**（= 单音上限 1.0 × 4 层 × 0.34 增益），整轨混音全糊。
  → 旋律铺设必须放在"每小节"循环**外面**，按 `range(0, bars, 4)` 铺。
  **这个 bug 只能靠量声部 RMS 抓出来**（编译过、跑得通、波形也正常）。
- **`analyze()` 的 `bar_samples` 是浮点数** → 用它做列表索引 `TypeError` → 静默崩溃
  （且 `--page >/dev/null 2>&1` 把错误吞了，表现为"表格没输出"）。

**坏消息（三条都是致命的）**：
1. **无容器 → 牌完全不叠**：12 张全落在 y=0.100，堆高 **0.000**。→ 「层」从来不是物理涌现的，
   是**布局作者指定的**（羊了个羊的层是画上去的，不是落出来的）。
2. **加容器 → 牌被挤得立起来**：堆高 1.59 = **8 张牌厚**（平放只应是 2~3 层），
   层数 5、每层 6:2:2:1:1（塔尖）。→ 与「麻将牌平铺」的视觉完全冲突。
3. **加容器 → 永不稳定**：静止漂移 **0.0898 ≈ 11% 牌宽**（4s 后还在动）；两次落定快照**不一致**

**结论**：要"真分层 + 遮挡可信 + 掉落可见"，正解是**确定性落定求解器**（自研，非引擎）：
层是数据结构（z 层号），每层平铺、层高 = 一个牌厚；遮挡按"更高层 + 真实占地相交"判；
拿掉支撑牌后用确定性算法算一次重力落定 + 回弹。→ 有物理感、可复现、零引擎体积。
**此结论已同步给用户，等他拍板是否改路线。**

### 20.3 ★★ 本轮最大的坑：**扩牌堆区单独做没有用，反而更糟**
`buildGrid` 原来是 `rows = floor(spanY / cellH) + 1` —— **网格永远把纵向填满**。
所以牌堆区从 664 扩到 762（+98）之后：spanY 涨 98 → 行数 8→10 → 行跨 479→616
→ **净结果下溢从 29px 恶化到 51px**。
改成**从"整堆装得下"反推行数**：
```
rowBudget = availY − (nFloors−1)×牌厚×GAP_MUL − 2×JITTER_Y − cellH×LAYER_OFFSET
rows = floor(rowBudget / cellH) + 1
```
（nFloors 必须用 `min(FLOOR.MAX, ceil(tileCount / FLOOR.PER))` 现算，不能读 level.layers）
→ 四关溢出**全部归零**（0/12），L4 视觉范围 -300~376 落在 -320~442 内。
教训：**任何"自适应填满容器"的算法，扩容前先问一句"它会不会把新空间吃掉"。**

### 25.2 错峰：田垄 → 随机成束（四步）
① 洗牌随机撒"束心"（束数 = 张数/6，夹到 3~6；用**洗牌**而非"随机抽到不重复"，保证必然终止）
② 每张牌归**最近**的束心（欧氏距离）→ 簇散落在牌堆各处，不是横竖的条
③ 束按**束心高度自下而上排序** —— "成束"管散、"排序"管方向，两件事分开管
④ 束内按**到束心的距离**往外铺开（`SPROUT_BURST_RING`）
④ 是**必要的**：L3/L4 每束 10~16 张，束内若同时冒会退化成"6 次大队列齐射"，成束感反而没了。
⚠️ 绘制顺序（siblingIndex）仍按 `depth`，只改先后。

新增 `BURST_SIZE/MIN/MAX/GAP/JITTER/RING`，删 `BAND_GAP/SWEEP_X/BAND_MAX`。

### 25.4 ★ 踩坑：`SPROUT_TOTAL_MAX` 的口径必须算"整段"
第一版算束间距时**只扣了单张升程** → 实测 L2~L4 跑到 **1.84s**（超预算 15%，用户要 1.6s）。
修正为扣「升程 + 落位回弹 + 束内抖动 + 束内铺开」→ 精确 **1.60s**。
实测：L1 = 3 束 / 1.53s；L2~L4 = 6 束 / 1.60s。

### 25.5 ★★ 方法论：动效的"编排"不能用截图连拍验收
S17 第一次连拍 L4，看到"第 9 帧（名义 860ms）就与终帧零像素差异"，一度以为入场只跑了 0.86s。
真因：**CDP `Page.captureScreenshot` 每张有几十~几百 ms 开销**，`wait:120` 累加出的"名义时间轴"
与真实相位完全对不上（同一串动作、不同次运行抓到的相位都不同）。

· 左（旧田垄）：颜色**严格按高度分层** + 阶梯状 → 就是"条带"。
· 右（新成束）：同一高度上**混着不同束**、时间散布到 0.8s，但**低处仍先冒** → 条带破了、方向还在。
→ 规则：**"顺序/编排"类改动用数据图验；截图只验"有没有播、终态对不对"。**

### 26.7 ★ 工具修复：`page-shot.mjs` 长页面"永久挂死"
两位专家各自独立撞到：整页截图在**超过约 8000px** 时**永不返回**（看着像 CDP 8s 超时，其实回不来）。
实测阈值：7291 / 7692 / 7847px 全部 0.6s 成功，**8108px 必挂**。
**根因不是慢，是渲染面尺寸上限（Chrome 约 8192px）**：旧写法 `captureBeyondViewport:true` 且不给 clip
＝要求把整页做成**一张**图面。把设备指标设成"整页那么高"也一样死 —— **换参数绕不过去**。
修复（`tools/page-shot.mjs`）：
- 先量 `scrollHeight`：**≤ 8000 整页截；> 8000 按 4000px 一段滚动着截**，输出 `out-1/-2/…`（已验证：13226px → 4 段，内容正确不重复）；
- **新增 `--el <选择器> [--scale n]`**：按元素包围盒截图，出高清稿用。
  这是"截设计稿里某一个手机框"的正解（不用手工算偏移，稿子改了也不会废）；
- 顺手记一个坑：`Runtime.evaluate` 返回 `{result:{type,value}}`，少写一层 `.value` → 高度算成 NaN →
  `setDeviceMetricsOverride` 报 `Failed to deserialize params.height`（报错完全看不出是取值写错）。

**同时修掉了 `cocos-to-wechat-minigame` 技能里一句错误的指导**（原文："长页面把高度给足，配 captureBeyondViewport
一次拍全"——这正是致挂的原因），并同步了技能里的 `scripts/page-shot.mjs`。
