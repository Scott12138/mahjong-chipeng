## 二、验证方法（为什么这份证据可信）

- **工具**：`tools/web-smoke.mjs`（无头 Chrome + CDP 直连，零依赖）。
  web-desktop 版与微信小游戏版**共用同一份 TS 逻辑**，所以在浏览器里点一遍 = 等价验证。
- **尺寸自检必须先过**：每次运行都要看到
  `✅ 引擎可见尺寸 = 设计分辨率 720×1280`，
  否则「设计坐标 → 屏幕坐标」的换算不成立，所有点击都不可信。
- **「吃」只可能在 L3 / L4 出现** —— 这是一个**推导结论，不是巧合**：
  `Generator.pickPatterns()` 给 L1 的「万」只发 2 个连号、L2 每族 2 个，
  **凑不出 3 连号**；**L3 才第一次出现 3 连号**（万/条各一组），L4 三族全有。
  这也顺带解释了「为什么此前所有自动化都从没见过『吃』」。
- 因此本轮用 `unlock:3` 直写存档跳到 **L3**，再用 **`dirty`** 策略
  （专挑槽内张数最少的牌、绝不凑 3 张）**自然逼出顺子**；
  而 `auto` 优先凑「碰」，**永远不会造出「吃」**。

### `生成器兜底量化/`

`probe.ts` 是**无头探针**：`Generator.ts` 只依赖 `CFG / TileData / MatchRule`（不含 `cc`），
所以可以用 Node 22 的 `--experimental-strip-types` **直接在纯 Node 里跑生成器**，
每关用 150 个随机种子，统计「硬崩」与「落在兜底」的比例。

```bash
node --experimental-strip-types --no-warnings probe.ts 150
```

| 关卡 | 修复前：开局硬崩（`best` 为 null → 关卡打不开） | 修复后 | 落在「兜底局」的比例（修复后） |
|---|---|---|---|
| L1 | 0 / 150 = **0%** | 0% | 0% |
| L2 | 1 / 150 = **0.7%** | **0%** | ~2% |
| L3 | 16 / 150 = **10.7%** | **0%** | ~11% |
| L4 | 63 / 150 = **42%** | **0%** | ~47% |

- `修复前-150次.txt` / `修复后-150次.txt` 是两次探针的完整输出。
- 全部硬崩**同一个根因**：约 **90% 的采样止步于 ①「开局可点牌 < 6」**，
  而那条分支 `continue` **排在兜底赋值之前** → 40 次全卡在 ① 时 `best` 恒为 `null`
  → `best!.tiles` 抛 `TypeError`。
- ⚠️ 修好「不崩」之后**仍有一条难度问题待拍板**：L4 有 **~47%** 的开局是
  「从未通过 ① 的兜底局」。是否可接受，见 DESIGN §11（**本轮不动，等用户拍板**）。

## 五、本轮修掉的两个缺陷（都属「报错指向错误方向」）

| 缺陷 | 症状 | 根因 |
|---|---|---|
| **`MotionFx.to` 传参形状错误** | 控制台被 `TypeError: Cannot read properties of null (reading 'length')` **每帧刷屏**（栈顶是引擎 `TweenAction.update`），但**不白屏**；同时「吃」的动效**静默失效** | 把 `chain`/`to2` 的 step 形状 `{props, duration, easing}` 误传给了 `to`（形参是 `(node, {position}, {duration, …})`）。引擎于是把 `props`/`duration`/`easing` 当**属性名**找，`Node` 上都没有 → `prop.start` 保持初值 `null` → **`typeof null === 'object'` 骗过引擎的类型分支** → 去读同样为 `null` 的 `prop.keys.length`。→ 修调用点 + 在 `MotionFx.to` 加运行时防呆 |
| **`Generator` 兜底是死代码** | 点第 3 关**没反应**，停在选关页 | ① 分支先 `continue`，兜底赋值排在后面（详见上节） |

> 教训：这两个 bug 的**报错位置都在引擎/生成器内部**，
> 但**根因都在调用方的一行参数**。
> 「每帧抛异常却不白屏」+「动效静默失效」是错误传参的典型组合特征。
