## 一、验收方法：无头点击冒烟

微信开发者工具**没有可编程交互接口**，命令行也看不到控制台；Cocos 画面是 canvas，
**无法用 DOM 选择器定位按钮**。但 web-desktop 版与微信版**共用同一份 TS 逻辑**，
所以在浏览器里点一遍即可等价验证（本工程的既有约定）。

```bash
# ① 构建（修完代码必须重建，否则验证的是旧产物）
bash tools/cocos-build.sh web-desktop debug game-4-mahjong

# ② 进第 1 关（unlock:0 = 全新档 → 主按钮进第 1 关）
bash tools/smoke-run.sh web-desktop /tmp/s18-teach-l1 \
     "unlock:0" "d:-56,-366@2800" "wait:1500"

# ③ 逼出「槽满判负」并连拍揉皱动效（fill 的 !<ms,...> = 判负帧连拍）
bash tools/smoke-run.sh web-desktop /tmp/s18-loss "unlock:1" "d:-56,-366@2800" "wait:1500" \
     "fill:24@620!120,300,520,760,1000,1300,1700,2200,3000"

# ④ 通关（auto 自动试玩）
bash tools/smoke-run.sh web-desktop /tmp/s18-pass "unlock:0" "d:-56,-366@2800" "wait:1500" \
     "auto:20@620!150,300,600,900,1200,1600"

# ⑤ 规则浮层（规则按钮在屏幕中轴上：setPosition(0, RULE_BTN_Y=531)）
bash tools/smoke-run.sh web-desktop /tmp/s18-rule-live \
     "unlock:0" "d:-56,-366@2800" "wait:1500" "d:0,531@900"

# ⑥ 开场墨晕分层取证（径向反解墨浓度，判据 = 平台档数 ≥3）
/usr/bin/python3 tools/probe-bloom.py <截图>
```

`d:<x>,<y>` 是**设计坐标**（原点 = 屏幕中心、y 向上，与 Cocos 一致），
所以点击坐标与 `CFG` 的布局常量一一对应 —— **读代码即可写测试，不用量像素**。

## 三、★★★★★ 本轮最重要的一条：`UIOpacity` 覆写是「一次性」的

> **这一条比界面本身更值钱** —— 它推翻了一条在本工程里已流传两轮的**错误结论**，
> 而那条错结论刚刚炸出了一次**全屏黑屏**。

### 3.1 旧结论（错）

> "`UIOpacity` 对 `Graphics` 不生效。"

### 3.2 新结论（引擎源码 + 像素取证双重确认）

```
① 引擎在 opacity「变脏的那几帧」，把子树每个顶点的 alpha 整个替换成级联值
     cocos/2d/assembler/utils.ts : updateOpacity()
         vb[i] = (vb[i] & 0x00ffffff) | (alpha << 24)      ← 替换，不是乘系数
   触发点：batcher-2d.ts 的 _handleUIRenderer()
         if (opacityDirty && vertexCount > 0) switch (render.getFillColorType()) {
             case COLOR:  updateOpacity(renderData, finalOpacity)   ← Graphics 走这支
             case VERTEX: /* do nothing */                          ← 只有 spine / dragon-bones
         }

② tween 一停就不再置脏；此后顶点数据一旦被重建
   （render-data 的 chunk recycle / allocate），alpha 就回落到
   Graphics 自己烘焙的 fillColor 值。

③ 于是「回落」的后果分两种：
     · 多档图形（四层墨晕）      → 回落成各层各自的 alpha → 分层会回来
     · 目标非 255 的单档图形     → 回落成 255 → 比设计值更不透明，且永不恢复
```

### 3.3 它怎么炸的（S18.5 失败动效）

失败动效的压暗层是一整块**全屏 INK 矩形**（`fillColor` alpha = 255），
上一版用 `UIOpacity` 淡到 `DIM_ALPHA = 0.10`：

| 时刻 | 现象 | 原因 |
|---|---|---|
| 0.27→0.45s | **看着完全正常**（薄墨压暗） | tween 每帧都脏 → 每帧被覆写成 25 |
| tween 一停 | **整屏变成不透明 `#22201C`** | 顶点被重建 → 回落成 255 |
| +3.7s | 仍全黑，失败面板"已开"却被盖住 | 永不恢复 |

**像素级取证**（这是把它钉死的关键 —— 只靠肉眼会误判成"Canvas 清屏黑"）：

```
s18-loss-l2/04-loss-300ms.png   中心 (237,230,212)  #ede6d4   正常
s18-loss-l2/04-loss-520ms.png   中心 ( 34, 32, 28)  #22201c  ← = CFG.COLOR.INK
                                四角与中心完全同值、纯黑像素占比 0%
s18-loss-l2/04-fill.png (+3.7s) 中心 ( 34, 32, 28)  #22201c  ← 仍全黑
```

时间点 `520ms ≈ RESET_START(0.27) + DIM_IN(0.18) = 450ms`，
**说明 tween 一直在跑、只是终点值没留住** —— 这条推理把方向从"动画没播"扳到了"值没生效"。

**修复后**（同一探针、同一条时间线）：

```
s18-loss-fix2/04-loss-300ms.png  中心 (237,230,212)
s18-loss-fix2/04-loss-520ms.png  中心 (216,210,193)   ← 比 300ms 暗一档，正是 10% 墨叠加 ✅
s18-loss-fix2/04-loss-1300ms.png 中心 (229,224,213)   ← 面板推入
```

对照图：`shots/00-修复前-全屏黑-对照.png` vs `shots/05-失败-揉皱溅墨压暗.png`。

### 3.4 由此确立的新判据（已写进 `UIFactory.ts` 铁律段）

> **只有两种情况可以用 `UIOpacity`：**
> ① 目标值 **0** —— 引擎里是硬开关（`visable = !approx(opacity, 0)`），整棵子树直接跳过渲染；
> ② 目标值 **255** 且整层内部单档 —— 因为"回落值"恰好就等于目标值。
>
> **凡目标值是中间值 → 一律用 `alphaPainter` 把 alpha 烘焙进 `fillColor` / `strokeColor`。**

按此复查全工程 **16 处** `UIOpacity`：只有失败动效的压暗层 1 处违规，已修。

⚠️ 顺带记一条**更隐蔽**的：**祖先的 `UIOpacity` 一样会抹平后代** ——
`PageManager.open()` 给每个页面节点挂了 UIOpacity 做 0.22s 转场淡入，
在那 220ms 内**整页所有 Graphics 的分层都是被抹平的**。

## 五、工具侧的本轮改进

`tools/web-smoke.mjs`：

1. **`fill` 动作支持连拍**（`fill:<n>@<gap>!<ms,...>`）—— 与 `auto` / `dirty` 同构。
   没有它就只能看到"已经揉完了"的末态。
2. **`fill` 的"搅牌兜底"** —— 原来的选牌策略只挑"点了不会凑成组"的牌，
   而叠塔结构会把**同一种牌面挤在一起先露出来**（实测 L4 开局可点 5 张里 4 张都是 `sou-6`），
   此时"凑 8 张互不成型的牌"**根本无解**，填到 7 张必卡死。
   现在无安全牌时会**主动消一组把牌堆搅开**（实测 L2 第 7、8 步搅牌 → 第 11 步判负 ✅）。
   ⚠️ 之所以敢这么做，是因为游戏判定顺序是
   **「入槽 → 先判消 → 没消成才判槽满」**（`GamePage.finish` 的调用点），
   所以点"会消的牌"不会判负，只会消掉 3 张、露出新牌。
3. 修正了 `fill` 的文档口径：它原写"**必定**逼出败局"，但受牌面组合限制**并不保证** ——
   现已改为准确表述，并补上搅牌机制。
