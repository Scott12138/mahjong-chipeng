方案 B ·「灯影牌楼」——把参考图1 的骨架留下，把它的木纹 / 大红 / 金整套换掉

这是三个方案里最接近参考图1 骨架、但视觉最不像参考图1的一个 —— 这个矛盾就是本方案要解的题。 骨架照抄它"顶部状态条 / 中央主视觉 / 底部一枚大按钮 / 两侧功能入口"的四段式， 但把木纹屏风 + 大红 + 金 + 棋牌语义文案整套换掉：底是深靛夜空，强调是暖灯黄， 主视觉从"圆形棋牌屏风"换成尖顶六边形灯罩（参考图2 的"圆形取景框 + 中央徽记"同样被改造）。

重心 / 两条自洽 / 与参考图的账

视觉重心顺序（第一眼 → 第四眼）

1

六边形灯罩里的牌阵。牌面是整页最亮的色（纸白 #FBF6EA 对罩内暗腔 #141B30 15.84:1， 保守按主体底 #1B2540 算也有 14.06:1）， 又独占屏幕正中心 + 两层光晕 + 罩内最暗的腔体（#141B30）反衬，全页只有这一块是"被打了光"的。

2

主按钮。暖灯黄 #E8A33D 的实色大块（520×124）+ 6px 立体厚度， 是全页面积最大的亮色块。它比牌阵弱一档、比其它元素强一档，正好卡在"要按的第一个东西"的位置。

3

顶部灯笼串 + 檐线。4 盏灯回答了"我玩到哪"。 刻意用暖黄（亮）对靛青（灭）的对比而不是数字，所以它比标题更先被看到 —— 这是有意的： 进度是玩家回到首页时最想确认的一件事，标题第二次看就够了。

4

两侧各一枚印章。x = ±298 等高对称（CFG +96），正好落进"檐的侧脸"让出的那两块空档里。竹青底（#3A5F45）+ 26px 纸白字（6.20:1）+ 18px 次级标签（7.16:1），是全页唯一的"冷色"角落，明确读作"这儿次要"。 刻意的取舍：这里不靠"把字调灰"压层级 —— 深底上降对比度最容易踩 4.5 那条线，层级一律由字号（26→18）+ 位置承担。 版本号这类"给开发看的"信息整个移出首页（进「关于」面板）。

删掉选关页之后的两件事（各给一个主张，不列选项）

① 从哪继续：主按钮 = 继续闯关 · 第 N 关（N = 已通关数 + 1），进入即直接开局，中间不再有任何选择页。 4 关全通后变成 再玩一遍 · 第 1 关（进度不清空，灯笼保持全亮）。按钮正上方还有一行「第 3 关 · 上道了」补全关卡名 —— 这样"继续"一词不必承担关卡名的信息。

② 怎么重玩 / 怎么清空：次按钮 = 重玩第 K 关（K = 最近通关的那一关；无记录时显示「重玩第 1 关」，可用）。 清空进度 = 长按次按钮 1.2 秒：按住时进度条在按钮正下方从 0 长到 352px，走满后弹出确认条「清空进度？／清空 · 算了」。
为什么不是"一枚独立小按钮"：清空低频且不可逆，独立按钮就等于在这一屏多加一个"会不会点错"的焦虑源，而这一版元素本来就比方案 A 多。 长按把入口成本抬到"刻意为之"且不占版面；再加一道确认条，是因为长按只防误触、不防"手滑按满"。两级保护，且都不引入新按钮。

③ 怎么跳着重玩某一关：不提供。这是删掉选关页的代价，也是有意的 —— 4 关的体量下，"跳关"是伪需求；真要回第 1 关，连清空进度一起做（长按 1.2 秒）， 代价比多养一个选关页低得多。

  • 借：主按钮"立体厚度 + 强色实底"，次级只给描边或小图标。

  • 换：圆形棋牌屏风 → 尖顶六边形灯罩（为什么不是圆，见下方整段）。

次要入口的两个状态（同一套 720 宽坐标）

左：长按进行中（进度条出现在次按钮正下方 44px）。右：走满 1.2 秒后弹出的确认条 （同一位置，不遮挡牌阵与主按钮）。两级保护：长按本身防误触 + 确认条防误清。

★ 关键差异点：为什么是尖顶六边形，不是参考图2 的圆

参考图2 的取景框是圆（月洞门）；本方案把它换成了尖顶六边形。 这不是"换个形状免得像"，四个理由按重要性排：

① 语义：我们要的是「灯罩」，不是「门洞」

参考图2 那个圆的职能是框住外面的景（取景框 / 月洞门）；本方案的形状要装东西（牌阵），职能是容器。 中式宫灯本来就是六角 / 八角灯，棱边是它作为「灯具」的身份特征；一旦做成圆，它就退回成"框"，和参考图2 撞得最狠。

② 构图：六边形与牌阵同构，圆形不同构

牌阵的轮廓是一个上窄下宽的梯形，而尖顶六边形的上半部正好是一个三角形 —— 梯形插进去时两条斜边与六边形的斜边近乎平行， 空出来的只是左右两窄条。换成圆，梯形四角会把圆的内侧切出四块大的月牙形空腔，牌阵在框里"发飘"； 要么缩小牌阵、要么加装饰填满 —— 两条路都比六边形贵。

③ 工程：六边形与瓦檐共用同一个原语

两者都是"多边形填充 + 折线描边"，一个新原语 fillPoly / strokePoly 同时喂两处；圆则是另一条 arc 路径。 在"元素比方案 A 多"的这一版里，少一类原语就是少一处要单独调的地方。

④ 形状谱系：与参考图2 整体拉开

参考图2 是「圆形取景框 + 圆形徽记 + 一道竖直光缝」；这里是「尖顶六边形灯罩 + 梯形牌阵 + 罩底光锥」。 三个图元全换了，只留下"中央有东西、被光照着"这一层抽象关系。

② 色板 —— hex / 用途 / 与现有 CFG.COLOR 的关系 / 实测对比度

对比度公式（WCAG 2.1 相对亮度法，我自己算的，不是估的）： L = 0.2126R' + 0.7152G' + 0.0722B'，每通道 c' = c/12.92 (c≤0.03928) 否则 ((c+0.055)/1.055)^2.4（c 为 0~1 的 sRGB）； 对比度 = (L_亮+0.05)/(L_暗+0.05)。阈值：正文 ≥4.5:1，大字（≥24px 或 ≥18.66px 粗体）≥3:1，非文字图形 ≥3:1。

与现有「牌从下方涌现」的关系：叠加在它之前，并且就地改写它的三个起点参数

现有实现（GamePage.playSproutMotion，S17 方案 B）：起点在目标正下方 1.2 个牌高、起始缩放 0.45、总时长 1.6s，随机成束错峰 + backOut 过冲 + 落位挤压回弹。新版叠加在它之前（不是替换） —— 涌现仍是"牌堆怎么上场"的唯一答案，但它不再承担"仪式感"。因此就地改写三处：

  • 起点 1.2 牌高 → 0.9 牌高：0.9 牌高≈罩底到牌堆顶的实测距离，牌看起来是从罩里出来的， 而不是"从屏幕外飞进来"。
  • 起始缩放 0.45 → 0.48：起手距离变短了，缩放再压到 0.45 会显得"从远处冲过来"，与"就在罩底下"矛盾。
  • 总时长 1600ms → 1000ms：仪式时间已经由掌灯给了，涌现要更干脆；否则两次"铺开"语义重复， 总时长会到 3.2s。
  • 被换掉的：错峰粒度从"随机成束（空间簇）"改为"按层（底→中→顶）"。 理由是掌灯之后玩家的期待是"按层显形"（罩内已经用层讲过一次）， 局内再打散成随机束，两段动效的"节奏语言"就不一致了。
  • 完整保留的：backOut 过冲、落位「挤压→回弹→过冲→归位」三段、落牌声节流、入场锁输入。

播完整版还是速版：每关首次进入播完整版（2550ms 后解锁）；重玩同一关 / 复活后重开播速版 （跳过 F3 的逐盏与 F4 的逐层：灯串 200ms 一次性全亮、牌阵 300ms 一次性显形 → 总 1500ms）。 判重只用一个内存标记（同一次会话内该关是否已播过完整版），不写存档 —— 这是"手感"不是"进度"，写进存档会让改一次时长就污染老玩家的档。

两条与现有代码的对接约定

① 灯串的 z 序在失败面板之上。失败面板 240ms 就进（这是玩家最需要的信息）， 而灯灭到 1400ms 才完。因此灯串节点必须挂在 modal 层之上（现在是 this._modalLayer 之下）。否则"灯一盏盏灭"会被遮罩压掉一半亮度， 观感变成"没播完整"。

④ 实现成本与风险

1 · 需要新增哪些绘制原语（全部是"纯色块叠加 + 描边"）

① 六边形（尖顶）+ 光晕

怎么画：6 个顶点一次算出来 —— for k in 0..5: a = −90° + 60k; (cx + R·cos a, cy + R·sin a)， 然后 moveTo → lineTo ×5 → close → fill()。 描边要重新走一遍同样的点再 stroke() —— Cocos 的 Graphics 里 fill() 之后路径不保留， 不能像 SVG 那样一次同时 fill+stroke。这是唯一一处"看起来一样但要写两遍"的地方， 建议在 UIFactory 加两个通用原语 fillPoly(g, pts, color, alpha) / strokePoly(g, pts, color, lw)（各约 10 行），后面几项全靠它们。

光晕 = 同一个六边形再描 2 次边（R = 198 / 206，alpha 0.16 / 0.09，内圈更亮）。 不用渐变、不用模糊、不用图层混合：由内到外变淡是靠两层低 alpha 叠出来的，不是算出来的 （想更柔就把 R 档位加到 3~4 层，成本是每层一次 strokePoly）。 这两圈是开口折线（只绕下部 5 个顶点、不闭合），光晕因此只出现在罩的下半部 —— 既符合"光从灯芯往上洒"，也避开了上部最贵的版面（标题）。实现上只是"传 5 个点、不 close"， 与闭合描边同一个原语，只差一个参数。

罩内短棱（6 条）用同一个 strokePath，以及罩底灯芯用 3 个同心 circle（r 24 描边 / 17 半透 / 8 实心）—— 都是已有原语，零新增。

② 瓦檐（檐面 + 瓦垄 + 重檐 + 檐口双线 + 椽头）

檐面：一个普通矩形 fillBox(g, 0, 552, 720, 176, 0, SHADE)（HTML 0~176 = CFG +640~+464）， 不是多边形 —— 檐从屏幕外压进来，玩家只看得到檐底，顶边本来就在画面之外。 这一条同时消掉两个麻烦：不会被胶囊拦腰截断，也不会读成往上的楼梯（第一版画成 8 顶点台阶就是这个毛病）。

瓦垄（1 条 strokePath 画 2 条横线，y = 60 / 110）：y = 60 那条落在胶囊带内， 所以 x 只到 496 就收笔；y = 110 那条不用管胶囊。
重檐（1 条开口 strokePath [(0,136)→(472,136)→(472,176)]）： 第三点不闭合，右端那一竖笔就是"檐的侧面"，把右上被让出来的空白解释成造型而不是"挖的洞"。
檐口双线（2 条全宽 strokePath，y = 176 / 185）：这是"国潮墨线双框"在新体系里的转译 —— 双框的结构记忆保留、颜色换成靛青 #33406B / #2A3760；它们比胶囊底边低 48px 以上，可安全走全宽。
椽头（27 条短竖线，x 16→692 步长 26，y 178→186）：一个 path 里 27 个子路径 （moveTo/lineTo 循环 27 次、只调一次 stroke()）—— 与现有 drawCorners 画朱红角花是同一手法，不是 27 个节点。

整个顶部区块合计 6 条路径、1 个 Graphics 节点（不同颜色之间改一次 strokeColor 即可， 不必拆节点），一次画完、永不重绘。灯要独立节点，因为它要动 opacity（见下条）。

③ 灯笼（亮 / 灭两个节点叠在一起）

形制：挂绳（折线）+ 上盖（小圆角矩形）+ 灯身（44 × 52、圆角 22 = 半圆头，圆角再小就读成方块） + 两条灯骨 + 灯芯（r = 11）+ 下盖 + 灯穗。全部是已有原语。

「熄灭」怎么做，是这里唯一需要拍板的技术选择：熄灭不是透明度归零（灯还在，只是不亮了）， 理论上要重绘颜色。本方案不重绘：每盏灯准备亮层 + 灭层两个节点叠在同一位置（尺寸完全一致、只有颜色不同 —— 亮层灯身 #E8A33D / 芯 #F6C877 / 盖与骨 #B87526，灭层灯身 #2A3760 / 描边与骨 #3A4670； 外圈柔光只在亮层有），熄灭 = 两层 opacity 交叉 180ms。 理由：逐帧重绘要给每盏改 5 个图形的颜色参数、4 盏 × 60fps，在微信上不划算； 而 opacity 交叉是引擎最省的通道（合批友好、零 CPU 路径计算）。 代价是节点数 ×2（共 8 个），静态几何各画一次 —— 这个交换在任何机型上都划算。

④ 光锥（"渐变"的纯色块替身）+ ⑤ 长按进度条

光锥：罩底灯芯往上洒的光，用一个梯形 fillPoly + alpha 0.06 表达。 这是刻意的近似：不追求连续过渡，只要"上淡下浓"的大感觉。 若评审觉得"一眼看出是块面"，叠 3 层梯形即可（alpha 0.04 / 0.03 / 0.02，逐层收窄、逐层变高）， 成本 +2 次 fillPoly。无论如何不用渐变 —— Graphics 没有渐变填充，而"叠低 alpha 实色"是它能力边界内的等价手段。

长按进度条：一个矩形槽 + 一个按 0→352px 改宽的实色矩形。刻意不用环形： 环形要用 24 段折线近似、每帧重绘线段数，而本方案元素已经比方案 A 多 —— 逐帧预算要全部留给开场动效（灯串点亮 / 牌阵显形才需要逐帧观察）。

2 · 贴图需求

0 张新增位图。全方案的所有效果都在 Graphics 的能力边界内实现： 圆角矩形（灯身 / 按钮 / 面板）、圆（灯芯 / 鼓点 / 金点 / 烟）、折线（檐线 / 椽头 / 灯骨 / 灯穗 / 挂绳 / 光晕）、 多边形填充（檐面 / 六边形 ×4 / 光锥）。包体不变，仍是 2.15 MB / 4 MB，余量 1.85 MB 一分没动。

唯一"看起来像贴图"的两处（光晕、光锥）都是纯色块叠加，已在上面给了做法与叠层参数。 如果将来确有某处必须靠位图（例如真的要做一盏写实灯笼），按本项目口径要单独标注体积； 本方案没有这样的地方。

3 · 适配 / 无障碍风险

风险 ①：深色底在低亮度户外手机上的可读性 （中风险，已有对策）

真实情况要先说清楚：深色底在阳光下"看不清"，原因几乎从不是对比度不足（对比度是相对量， 屏幕再暗，纸白与深靛的比值仍是 12.98:1），而是屏幕反射光把整个画面提灰， 于是"暗部不再是暗部"、"亮部还是亮部"，中间的次级信息先糊掉。

对策（三条，都在设计里落死）：

  1. 全页最亮的一块留给唯一的操作：主按钮是灯黄实底 + 深靛字（7.92:1）， 它是"亮面 + 暗字"，在反光环境下比"暗面 + 亮字"更抗打 —— 任何时候玩家都能找到"下一步点哪"。
  2. 正文一律 ≥ 6.20:1，一条例外都没有（最弱的是印章上 26px 的纸白字对竹青底 6.20:1， 其次是次按钮灯黄字对夜景底 7.92:1、次级文字 #A9B2CB 7.16:1）。 不是"刚好 4.5" —— 深底上不给自己留"刚刚达标"的余量。
  3. 层级一律由字号 + 位置承担，不由对比度承担。 这一版把上一稿里那行 15px 的"#6E7799 装饰文字"直接取消了（它当时只有 3.44:1）： 底部操作说明改用 #A9B2CB（8.07:1，字号仍是最小的 15px）， #6E7799 只剩"画线"的活儿（分镜箭头 / 分隔线，走非文字图形的 3:1）。 深底上"用灰做层级"是最容易踩线的一招，这一版干脆不用 —— 于是"不达标就返工"这条在整份稿里没有触发点。

风险 ②：微信右上角胶囊压在瓦檐上 （高风险，必须在设计里解决）

这个风险是真实的：微信小游戏的胶囊按钮由系统绘制在最上层，位置在右上角， 典型占位在设计分辨率下约 248 × 88px（x 约 496~720、y 约 40~128）。 任何横向贯穿顶部的线条（檐口、分隔线、装饰带）都会被它"从中间截断"，看上去就是一次渲染错误 —— 而这个页面本身就是"一条檐横贯顶部"的构图，正面撞上。

解法（不是妥协，是设计里主动用掉它）：

  1. 先改变檐的"读法"：檐从屏幕外压进来，玩家只看得到檐底，檐面是 x 0~720 / y 0~176 一整块实色、没有"屋顶的顶边"。这一刀同时办两件事 —— （a）不存在"被胶囊从中间截断"的那条顶边，因为本来就没有顶边； （b）也不会读成"一级级往上的楼梯"（第一版画成台阶就是这个毛病）。
  2. 唯一的横向装饰线是瓦垄（y = 60 / 110）。其中 y = 60 落在胶囊带内， 于是它 从 x = 496 就收笔（正好是胶囊左边界）—— 玩家看到的是"瓦垄画到右边就没了"， 而不会有东西被胶囊拦腰切断。
  3. 檐口双线（y = 176 / 185）与椽头 27 条（y 178~186）都比胶囊底边低 48px 以上，可放心走全宽 —— 这是"檐横贯顶部"的构图能保住的原因。
  4. 重檐右端在 x = 472 立下去收口（M0 136 H472 V176，这一竖笔就是檐的"侧面"）， 顺手把"右上这块被让出来"解释成了檐的侧脸而不是留白。 两枚小印章于是 x = ±298 等高对称（CFG +96）分列左右、把灯罩框在中间 —— 既各自落进"檐的侧脸"让出的那块空档里，也顺手把首页的左右配重拉平，右侧不至于空成一片。

兜底：真机上胶囊的实际尺寸随机型 / 系统版本变化（iOS、Android、开发者工具预览三处都不一样）。 落地时按 CFG.SCREEN.TOP_SAFE = 100 的口径再校一次： 若实测胶囊底边低于 y = 118，就把重檐那一笔的整体 y 从 136 等量下移（重檐高度本来就是自由量）， 并把 y = 60 那条瓦垄整条删掉（只剩 y = 110，檐面就不需要开这个口了）。

风险 ③：与「休闲益智」类目的契合度 （这是本方案最大的收益点）

去掉的东西：朱红 #C4362B、金 #C9A227、木纹、棋牌语义文案（含上表点名的「碰 / 吃 / 杠」那一行）， 以及参考图1 里"称号 + 战绩 + 榜单"这一整类竞技与炫耀语义。词和概念一个都没抄。

剩下的语义：灯笼、夜色、关卡进度、闯关。这是一个场景，不是一张牌桌。 深靛 + 暖灯黄 + 竹青，与"棋牌红金"没有任何一色重叠。

唯一残留的红在牌面上（万子的「萬」、筒族红、牌角花），这是刻意的保留： 牌面 27 张是已定稿资产，不得重新设计；而且界面一旦不再是红的， 牌面上那点红反而成了全页唯一的红 —— 三族的区分度（蓝 / 红 / 绿）因此比现在更强， 而全页也不再读作"红底红牌"。

须知的风险点：若审核员把"牌面图案本身"读作麻将，那是牌面资产的问题，与本次界面改版无关， 按 README §7 的约定提审前用 minigame-publish-compliance 单独复核。 本次改版把"界面层"这一半的合规风险清掉了（三个方案里唯一直面的一个）。
